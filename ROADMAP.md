# Roadmap

Ideas under consideration, not commitments. Items land here when they survive a discussion, and they leave by shipping or by being written off in [CONSIDERATIONS.md](notes/CONSIDERATIONS.md).

- **Non-Claude subscription profiles.** Profiles are data, so a GPT or Kimi coding-agent subscription should slot in as one more entry in `profiles.json` with its own `tool` and wrapper. The plumbing exists, but nothing has exercised it against a real second tool yet.
- **Per-profile provider data.** Borrowed from cc-switch. If a profile ever needs a non-default endpoint or provider settings, that belongs in its `profiles.json` entry rather than in hand-edited config files.
- **Headroom visibility.** Borrowed from cc-switch's usage dashboard. The resource being managed is which account has room left, and today nothing shows it. Partly answered from outside this repo: the `headroom` skill in [ilano-skills](https://github.com/ryanilano/ilano-skills) reads `profiles.json` for its roster and reports every profile's caps, pacing, and credential state, then names the account to work on. What is still missing here is the terminal path: a `maxx headroom` subcommand that shells out to the same script, so the answer does not require a Claude session.
- **Multi-provider headroom.** The interesting version of the above, and the hard one. Once profiles can be a Claude Max account, a GPT subscription, and a Kimi plan at once, "which account has room" stops being a lookup and becomes arbitrage across incompatible units: providers meter differently (tokens, requests, messages, credits), reset on different anchors and cadences, weight models differently against a shared cap, and mostly do not expose a usage endpoint at all. A useful answer would have to normalize headroom across those units and account for what each provider is actually good at, since the cheapest remaining quota is not always the right tool. Big enough that it should not be bolted onto the per-account reporting; it wants its own design pass.
- **`maxx pin` cannot reach the editor extension.** `pin` writes `terminal.integrated.env.osx/.linux`, which only reaches integrated terminals. The Claude Code editor extension (VS Code, VSCodium) launches its own process and never reads those keys, so a repo pinned to `fyi` still opens the extension on whatever the default config dir is logged into. Silent wrong-account sessions are exactly what `pin` exists to prevent, so today the guarantee has a hole in it and nothing says so.

  The extension does expose two settings that would do the job, verified 2026-08-13 against `anthropic.claude-code` 2.1.226:

  - `claudeCode.environmentVariables`, an array of `{name, value}` pairs, which can carry `CLAUDE_CONFIG_DIR` directly.
  - `claudeCode.claudeProcessWrapper`, an executable path, which the existing `~/bin/claude-<name>` wrapper drops straight into. Note this also swaps which `claude` binary runs, since the wrapper resolves it from PATH rather than using the one bundled in the extension directory.

  Both are `"scope": "machine"`, and machine-scoped settings are ignored in a workspace `.vscode/settings.json`. So this cannot be per-repo the way `pin` is. The account choice for the extension is machine-wide, per editor (VS Code and VSCodium keep separate user settings, so one account each is possible), or per editor profile if machine scope turns out to be profile-aware, which is untested.

  Two things to decide. First, whether `pin` should detect an installed extension and warn that the pin does not cover it, rather than reporting success that is only half true. Second, whether the user-settings side belongs in maxx at all or stays out of scope. A throwaway prototype lives at `~/bin/cc-mode` (not in this repo, not managed by maxx): it reads the roster from `profiles.json` and flips `CLAUDE_CONFIG_DIR` plus `claudeCode.useTerminal` in the editor's user settings. It works against VSCodium and fails against VS Code, whose `settings.json` is JSONC and cannot be parsed by `jq`. That JSONC problem would have to be solved before any of this shipped here.

- **Re-evaluate cc-switch** if API relays or non-Claude providers enter the picture. The conditions are written down in [CONSIDERATIONS.md](notes/CONSIDERATIONS.md).
